## 2. 서비스 한 줄 정의

Fridgely는 개인 또는 공동 냉장고의 식재료와 유통기한을 관리하고, 임박·만료 재료를 놓치지 않도록 알림을 제공하며, 현재 재고를 활용할 수 있는 요리를 추천하고 실제 조리 시 재고 차감까지 연결하는 모바일 웹/PWA 서비스다.

핵심 사용 흐름은 다음과 같다.

```text
OAuth 로그인
→ 개인 냉장고 생성
→ 재료 등록·관리
→ 임박·만료 알림 확인
→ 현재 재고 기반 요리 추천
→ 요리 적용 및 재고 차감
→ 필요하면 공유 냉장고에 참여해 공동 관리
```

### 버전별 기능 분류

기능마다 어느 버전 범위인지 표시한다. `O`는 해당 버전에서 제공, `—`는 제공하지 않음, `확인 필요`는 근거 자료에서 버전을 확인하지 못한 항목이다. **`확인 필요` 항목은 팀이 버전을 확정하기 전까지 추정으로 채우지 않는다.** 구현 전에 이 표에서 요청 기능의 버전을 확인하고, 범위 밖이거나 `확인 필요`이면 먼저 알린다.

## 3. 인증 구조

### 인증 수단

- 카카오·구글 OAuth 로그인이 v2·v3의 기본 인증이다.
- 서비스의 실제 회원 본체는 `users` 한 행이다.
- `social_accounts`는 그 회원에게 접근하는 인증 수단이다. 어떤 OAuth 경로로 로그인하더라도 연결된 동일 `users`를 가리킨다.
- OAuth 로그인 식별자는 이메일이 아니라 `(provider, provider_user_id)`다.
- `provider_email`은 OAuth 제공자가 준 이메일 스냅샷이다. 로그인 키가 아니며 UNIQUE를 걸지 않는다.
- 서로 다른 OAuth 계정을 한 회원에게 연결하는 계정 연동 UX는 현재 빠져 있는 후속 기능이다.

### 로컬 인증 통합 (2026-09-07 확정)

- v1의 아이디·비밀번호 인증은 별도 `local_accounts` 테이블이 아니라 `users`에 통합한다. ERD에서 `local_accounts` 도형은 삭제됐고 이전 정의는 정의서의 이력 카드에 남아 있다.
- `users.login_id` VARCHAR(10) NULL 허용 UNIQUE. 영문·숫자 2~10자의 로그인 아이디이며 이메일이 아니다.
- `users.password_hash` VARCHAR(60) NULL 허용. bcrypt 해시만 저장하고 원문은 저장하지 않는다.
- 두 필드는 모두 NULL이거나 모두 NOT NULL이어야 한다(CHECK).
- `users.password_changed_at` DATETIME(6) NULL 허용. 비밀번호 변경 이전에 발급된 토큰의 무효화 기준이며 OAuth-only 회원은 NULL이다.
- OAuth-only 신규 회원은 세 필드가 모두 NULL이다. 이를 정규화 위반으로 보지 않는다.
- 통합은 구조 단순화를 위한 선택이며 JOIN 제거로 성능이 개선됐다는 측정 결과는 없다.
- ERD 도형 삭제가 운영 DB의 인증 데이터 이전·삭제를 뜻하지 않는다. 실제 이전은 별도 검증 대상이다.

## 4. 회원과 탈퇴

### 회원 기능

- OAuth 인증 후 닉네임과 프로필 정보를 설정한다.
- 닉네임은 2~10자이며 서비스 전체에서 중복될 수 없다.
- 닉네임 설정·변경 시 형식, 중복, 금칙어를 검사한다.
- 회원은 프로필 정보와 닉네임을 조회·변경하고 로그아웃할 수 있다.
- 회원은 임박·만료(`EXPIRATION`) 알림과 추천(`RECIPE`) 알림 수신 여부를 각각 설정할 수 있다.
- 마이페이지의 전체 알림 스위치는 두 하위 설정이 모두 ON일 때만 true다. 하나라도 OFF이면 전체 스위치도 OFF로 표시한다. 전체 스위치를 직접 바꾸면 하위 설정을 모두 같은 값으로 원자 갱신하고, 개별 OFF는 다른 하위 설정을 끄지 않는다. 별도 전체 스위치 컬럼은 추가하지 않고 기존 `notification_preferences`를 사용한다.
- 가입 시 회원 본체, 인증 계정, 개인 냉장고, OWNER 참여 관계가 만들어진다.

### 탈퇴 정책

- `users`는 즉시 물리 삭제하지 않고 `WITHDRAWN` 상태와 `deleted_at`을 남긴 뒤 개인정보를 익명화하는 soft delete 대상이다.
- 인증 차단은 `login_id`·`password_hash`·`password_changed_at`을 NULL로 비우고 `social_accounts` 연결을 제거하는 방식으로 처리한다.
- 모든 기기의 refresh token을 폐기하고 푸시 구독을 즉시 비활성화한다. 만료 전 access token도 탈퇴 계정 접근을 차단한다.
- **소유권 이전은 자동 위임이다.** OWNER가 탈퇴하면 남은 유효 구성원 중 `created_at ASC, refrigerator_member_id ASC`의 첫 구성원에게 자동으로 위임한다. 수동 소유권 이전 API·UI는 제공하지 않는다.
- `is_active`는 현재 냉장고 선택 값이므로 후임 자격 판정 필터로 쓰지 않는다. 탈퇴 회원은 후임에서 제외한다.
- 냉장고·참여 관계 잠금 아래 남은 구성원을 재확인하고 기존 OWNER 해제·후임 지정·탈퇴를 같은 트랜잭션으로 처리한다.
- 공유 냉장고와 그 재고는 다른 구성원이 사용하므로 소유자의 탈퇴만으로 삭제하지 않는다.
- **마지막 구성원이 탈퇴하면** `refrigerators.deleted_at`에 삭제 시각을 기록해 즉시 soft delete한다. 복구 유예는 없으며 조회·가입·재고 변경·추천·푸시를 차단한다.
- 회원 탈퇴에서 하위 데이터를 일괄 CASCADE 삭제하지 않는다. 보관 목적·기간이 끝난 뒤 자식 FK 참조부터 정리하고 냉장고를 마지막에 hard delete한다. 보관 기간 확정 전에는 hard delete를 실행하지 않는다.
- 종료한 참여 이력의 보존 방식은 미결이다. `is_active=false`만으로 탈퇴·추방 상태를 표현했다고 보지 않는다.
- 인메모리 추천 캐시는 탈퇴 및 냉장고 접근 종료 시 즉시 퇴출한다.
- 같은 OAuth 또는 `login_id`로 재가입하더라도 새 `users`가 생성되며 예전 냉장고·알림·활동 이력을 자동 복구하지 않는다.

## 5. 냉장고와 공유

- 회원에게는 기본 개인 냉장고가 하나 있다.
- `refrigerators`는 냉장고 자체를, `refrigerator_members`는 회원과 냉장고의 N:M 참여 관계를 나타낸다.
- OWNER 여부는 `refrigerator_members.role`로 관리한다. `refrigerators`에 소유자 FK를 중복 저장하지 않는다.
- 한 회원은 여러 냉장고 참여 이력을 가질 수 있지만 현재 활성 냉장고는 정확히 하나다.
- `is_active`는 현재 보는 냉장고를 표시한다. 개인·공유 유형이나 탈퇴·추방 상태를 대신하지 않는다.
- `active_marker`의 UNIQUE 제약으로 회원당 활성 냉장고가 둘 이상 생기는 것을 DB 수준에서 막는다. 정확히 하나가 존재하는 것은 전환 트랜잭션이 보장한다.
- 공유 냉장고에 참여하면 개인 냉장고와 데이터는 삭제하지 않고 비활성 상태로 보존한다. 참여 중에는 개인 냉장고를 관리할 수 없다.
- 공유 냉장고 탈퇴 시 개인 냉장고를 다시 활성화한다. 공유 냉장고의 재료를 개인 냉장고로 가져갈 수 없다.
- 공유 냉장고의 최대 인원은 4명이며, 초대·추방·소유권 위임·전환은 냉장고 단위 잠금으로 직렬화하고 정원과 유효 OWNER를 재검증한다.
- 초대 코드는 영문 대문자·숫자 6자리이며 코드 자체는 UNIQUE다. 재발급할 수 있으므로 냉장고 ID에는 UNIQUE를 걸지 않는다.
- 냉장고 이름은 생성 시 소유자 닉네임으로 초기화하지만 이후 독립적으로 관리한다.
- **마이페이지 집계**: `refrigerators.expired_count INT NOT NULL DEFAULT 0`, `expired_count_month CHAR(7) NOT NULL`(YYYY-MM). 이번 달 만료 재고 행 수를 누적하고 재고 삭제 후에도 유지한다. 월 전환 시 월과 카운트를 원자적으로 초기화한다. 과거 월별 이력은 보관하지 않는다. 집계 월은 월 전환 누락 판별용이며 재고별 중복 집계 방지 수단이 아니다.
- **`refrigerator_type`은 아직 컬럼에 없다.** 개인·공유를 냉장고 자체의 속성으로 구분하자는 제안(VARCHAR(20), 기본값 PERSONAL, CHECK IN ('PERSONAL','SHARED'))이 있으나, 팀의 "개인 냉장고를 공유로 전환" 방식과 API 초안의 "별도 생성" 흐름이 어긋나 PL 재확인 후 확정한다. 구성원이 한 명이라는 사실로 개인 냉장고를 추론할 수 없다.

## 6. 재료 등록과 재고 관리

### 등록·조회 기능

- 사용자는 재료를 직접 입력하거나 이미지/OCR 인식 결과를 확인해 등록할 수 있다.
- OCR의 중간 결과는 영속 테이블을 늘리지 않고 처리 중 데이터로 다룬다. 사용자가 확정한 결과만 `ingredients`에 저장한다.
- OCR 인식 상태는 `RECOGNIZED`·`UNRECOGNIZED`·`NEEDS_REVIEW`·`AI_ESTIMATED` 네 가지다. AI 추정은 유통기한 표기 자체가 없을 때만 허용하고, 표기가 있는데 판독에 실패한 경우는 사용자 확인 대상이다.
- 재료에는 이름, 카테고리, 냉장·냉동 보관 방식, 측정값, 유통기한, 선택 이미지가 있다.
- 현재 활성 냉장고의 재료 목록과 상세 정보를 조회하며 재료명으로 검색할 수 있다.
- 보관 방식, 카테고리, 재료 상태로 필터링하고 유통기한, 등록일, 이름 등을 기준으로 정렬할 수 있다.
- 재고 상태 값은 `EXPIRING_SOON`·`EXPIRED`(+정상)이다. 이전의 `EXPIRING` 표기는 알림 유형과 맞추어 `EXPIRING_SOON`으로 통일한다.
- 카테고리는 채소, 과일, 육류, 수산물, 유제품, 두부·콩, 곡물·면, 가공식품, 조미료, 음료, 기타를 사용한다.
- 카테고리는 필터 표시용 보조 정보이므로 정확도 로직에 투자하지 않고 사용자 입력값을 그대로 저장한다. OCR·실물 인식 등록일 때만 AI가 자동 분류하고 결과는 등록 전에 사용자가 확인·수정한다. 재고 수정 시에는 AI가 개입하지 않는다.
- 냉장고별 재고 등록 상한은 기본 100종이다. 고정 숫자를 애플리케이션 곳곳에 박지 않고 `refrigerators.capacity`를 읽어 검증한다.
- 같은 이름의 재료라도 보관 방식이나 유통기한 등이 다르면 별도 행으로 존재할 수 있으므로 재료 이름에는 UNIQUE를 걸지 않는다.
- 재료 상태와 D-day는 `expiration_date`와 오늘 날짜로 계산하며 중복 저장하지 않는다.

### 측정 방식

재료는 다음 둘 중 정확히 하나의 방식으로 측정한다.

| 방식 | quantity | weight_value | weight_unit |
|---|---:|---:|---|
| COUNT | 1~100 | NULL | NONE |
| WEIGHT | NULL | 0 초과 | G 또는 ML |

- `measure_type`이 COUNT 또는 WEIGHT 중 어느 값이 유효한지 명시한다.
- kg와 L 입력은 저장 전에 G와 ML로 환산한다.
- DB CHECK로 두 조합 중 정확히 하나만 성립하도록 막는다.
- `weight_value`는 정확한 십진 계산이 필요한 측정값이므로 근삿값인 FLOAT/DOUBLE 대신 `DECIMAL(10,3)`을 사용한다.

### 변경 기능

- 재료 등록, 수정, 수량 변경, 삭제를 지원한다.
- 요리 적용 시 사용 재료를 차감한다.
- 재고 변경은 추천의 기준이 되는 재고 지문을 바꾸지만 변경 시점에 AI를 바로 호출하지는 않는다.

## 7. 레시피 사본

**2026-09-07 확정.** 이전 판의 "우리 서비스는 레시피 원본을 관리하지 않는다"는 서술은 폐기됐다.

- AI가 레시피 원본의 수집·정규화·추천 알고리즘을 담당하고, 백엔드는 서비스 조회·권한·차감을 담당한다.
- 백엔드는 조회용 **사본**을 `recipes`·`recipe_ingredients`·`recipe_steps` 3종에 보관한다. 반복 집합인 재료와 단계는 자식 테이블로 분리한다.
- `recipes`: `recipe_id` BIGINT PK, `source` VARCHAR(32), `source_recipe_id` VARCHAR(191), `source_revision` VARCHAR(128), `name`, `image_url`, `base_servings` DECIMAL(10,3), `status`(ACTIVE/INACTIVE), `synced_at`.
- UNIQUE(`source`, `source_recipe_id`)로 동일 원천 레시피의 중복 적재를 막는다. `source_recipe_id`는 `utf8mb4_bin`으로 대소문자를 구분한다.
- `source_revision`은 원천 버전 토큰이다. 문자열 대소 비교로 최신 순서를 판단하지 않는다.
- `recipe_ingredients`: `recipe_ingredient_id` PK, `recipe_id` FK, UNIQUE(`recipe_id`, `ingredient_no`). `name`, `amount_text`, `measure_type`(COUNT/WEIGHT/VOLUME/UNKNOWN), `amount_value`, `unit`.
- `recipe_steps`: `recipe_step_id` PK, `recipe_id` FK, UNIQUE(`recipe_id`, `step_no`). `instruction`, `image_url`.
- 레시피 하위 테이블도 BIGINT 단일 대리키를 쓰고 업무상 번호는 UNIQUE로 제한한다. 복합 PK 자체를 안티패턴으로 보지는 않지만, FK 참조·ORM 식별자·API 표현을 단순하게 하기 위한 팀의 선택이다.
- **`recipe_ingredients`는 사용자 재고 `ingredients`를 FK로 참조하지 않는다.** "소금 약간" 같은 표현은 원문을 보존하고, 검증된 수량 변환이나 사용자 확인 없이 자동 차감하지 않는다.

### 동기화 (설계만 반영, 운영은 계약 후)

- 생성: 최초 전체 적재 후 주기적 증분 API로 생성.
- 변경: 원천 키로 멱등 upsert, 역순 버전 차단. 부모·재료·단계를 하나의 트랜잭션으로 갱신하고 목록이 유효한지 검증한 뒤 공개한다.
- 삭제: 명시적 삭제 이벤트나 완전한 전체 스냅샷 대조로 INACTIVE 처리. **API 장애를 원천 삭제로 해석하지 않는다.**
- 보관: 실패 시 마지막 정상 사본을 제공한다. 자식은 부모 삭제 시 CASCADE, 조리 기록이 참조하는 부모는 RESTRICT.
- 성공 커서와 마지막 성공 시각은 내구성 있는 작업 저장소에 보존한다.
- **아직 합의되지 않은 계약**: 안정 ID, revision 순서, 증분 커서·페이지, 삭제 표시, 단위, 동기화 주기·허용 지연·재시도, ID 없는 생성형 레시피 지원 여부.

## 8. 요리 추천

### 추천 결과의 소유

- 레시피 본문은 위의 사본 테이블에서 조회한다. **인메모리 캐시에 남는 것은 냉장고별 추천 결과**(추천 순위, 필요량, 보유·부족 계산)다.
- 저장소는 Redis가 아니라 애플리케이션 인스턴스 내부 인메모리 캐시다.
- 캐시 기준은 냉장고 ID, 현재 재고 지문(SHA-256 16진수 64자), 만료 재료 포함 여부다.
- 홈 카드, 추천 목록, 추천 푸시는 같은 추천 목록을 공유한다.
- **최신 레시피 갱신이 과거 추천의 필요량·차감량을 바꾸지 않는다.**

### 추천 방식과 순위

- 추천은 AI가 재료로 요리를 만들어내는 방식이 아니라, 이미 존재하는 레시피 중 보유 재료로 만들 수 있는 것을 찾는 방식이다.
- 부적절한 재료 조합은 필터링하지 않는다.
- AI는 추천 요리와 요리별 필요 재료·수량을 생성하고, 서버는 필요량과 보유량을 비교해 미보유·부족·적합을 계산한다.
- 정렬 우선순위(재료 **종류 수** 기준):
  1. 임박 재료 종류 수 내림차순
  2. 부족·미보유 재료 종류 수 오름차순
  3. 보유 재료 종류 수 내림차순
- 추천 목록에서는 상태만 표시하고 정확한 개수·g·ml는 요리 상세에서 보여준다.
- 소금·물처럼 재고 수량으로 비교하기 어려운 재료는 상세에 포함하되 미보유가 아니라 **별도 준비 재료**로 표시한다.
- 추천 화면의 정렬 변경은 기존 결과만 재정렬하며 새 AI 요청으로 세지 않는다.

### 생성과 갱신

- 재고 등록·수정·수량 변경·삭제·요리 차감 시점에는 AI를 바로 호출하지 않는다. 유통기한을 여러 번 수정해도 최종 재고 기준으로 한 번만 호출되므로 별도 배치 주기를 두지 않는다.
- 홈 또는 추천 페이지에 진입할 때 현재 재고 지문과 일치하는 추천이 있으면 그대로 보여준다.
- 일치하는 결과가 없지만 이전 추천이 있으면 이전 결과를 먼저 보여주고 새 결과를 비동기로 한 번 생성한다.
- 비동기로 완성된 결과는 사용자가 보고 있는 화면을 갑자기 교체하지 않고 다음 신규 진입부터 보여준다.
- 이전 결과도 없는 최초 진입에서는 준비 중 화면을 보여주고 생성 완료 후 결과를 표시한다.
- 동일 냉장고·동일 재고 지문의 동시 생성 요청은 `ConcurrentHashMap.computeIfAbsent`와 공유 `CompletableFuture` 방식으로 하나만 실행한다. 단순 불리언 조회 후 설정으로 대체하지 않는다.

### 만료 재료와 한도

- 기본 추천은 만료 재료를 포함한다(`INCLUDE_EXPIRED`). 실제 섭취 가능 여부는 사용자가 판단한다.
- 만료 재료가 있을 때만 "만료 재료 빼고 추천받기"를 노출한다(`EXCLUDE_EXPIRED`).
- 제외 요청은 기존 결과를 대체하는 새 생성이므로 확인 모달을 거친다.
- 새 추천 생성은 냉장고당 하루 최대 10회다. 07:55 사전 준비 생성도 이 한도에 포함된다.
- 일일 생성 한도에 도달하면 마지막 추천 목록을 유지하고 한도 도달 안내를 표시한다. 남은 횟수를 상시 표시하지는 않는다.
- 재고가 그대로여서 캐시를 다시 보여주는 것, 정렬만 변경하는 것, 기존 추천으로 푸시하는 것은 횟수에 포함하지 않는다.
- 현재는 `ConcurrentHashMap<(refrigeratorId, count_date), AtomicInteger>`로 제어하므로 서버 재시작 시 초기화되고 다중 인스턴스 간 한도를 공유하지 못한다.

### 추천 푸시

- 매일 07:55에 현재 재고와 맞는 추천 결과가 있는지 확인하고, 없으면 일일 한도 안에서 새로 생성한다.
- 매일 08:00에 목록의 다음 순번 요리 한 건을 푸시한다(Asia/Seoul 기준).
- 목록 끝까지 보내면 다시 첫 번째 요리로 돌아간다. 새 추천이 생성되면 푸시 순번도 첫 번째부터 시작한다.
- 추천 푸시는 앱 알림함에 저장하지 않는다. `notifications`·`notification_recipients`에 행을 만들지 않는다.
- 푸시 클릭 시 특정 과거 요리 상세가 아니라 현재 추천 페이지를 연다.
- 발송 재시도는 추천을 재생성하거나 순번을 다시 증가시키지 않는다.

## 9. 조리 기록

- 테이블명은 `cooking_records`, 논리명은 **조리 완료 기록**이다. 저장 대상은 "적용 기능"이 아니라 완료된 조리의 사실이다. 이전 이름 `cooking_applications`는 폐기했다.
- PK는 `cooking_record_id`, 완료 시각 컬럼은 `cooked_at`이다.
- 사용자가 요리 상세에서 적용하기를 누르면 현재 냉장고의 사용 재료를 차감한다.
- 백엔드가 현재 재고·재료 매칭·필요량을 재검증한다. 기준 인분만큼 적용하며 별도 인분 변경은 없다.
- 충분하면 필요량만, 부족하면 보유량만 차감하고 미보유 재료는 건너뛴다. 필요량 수치화·단위 환산이 불가한 재료는 차감에서 제외한다.
- 차감할 재료가 없어도 요리 적용은 성공한다. 재료 부족·미보유 자체는 오류가 아니다.
- 재료 차감, 조리 기록 생성, 본인 누적 요리 수 +1은 하나의 트랜잭션이다.
- 클라이언트 요청의 `idempotency_key`에 UNIQUE를 걸어 연속 클릭·재시도로 같은 요리가 두 번 차감되는 것을 막는다.
- 캐시가 사라져도 적용 기록을 설명할 수 있도록 당시 요리명을 `recipe_name_snapshot`으로 보존한다. 레시피 FK 유무와 관계없이 저장한다.
- **`cooking_records.recipe_id` FK와 `recipe_revision_snapshot` 추가는 미정이다.** 모든 추천에 원천 ID가 있는지 확인하기 전에는 필수 FK로 만들지 않는다.
- 적용 직후 뒤로 가면 사용자가 보던 기존 추천 목록을 유지한다. 홈·추천 페이지에 새로 진입할 때 최종 재고 기준 갱신을 판단한다.

## 10. 알림

### 알림 종류와 저장 범위

- 알림 유형은 5종이다: `EXPIRING_SOON`, `EXPIRED`, `MEMBER_JOINED`, `MEMBER_LEFT`, `MEMBER_KICKED`.
- 추천 요리는 일회성 푸시 제안이므로 앱 알림함에 쌓지 않는다.
- `notifications`는 냉장고에서 발생한 공통 제목·본문이고, `notification_recipients`는 어떤 회원이 받았고 언제 읽었는지를 나타낸다.
- **알림 대상 연결(`notification_targets`)은 미채택으로 확정했다.** 알림 클릭이 재고 목록의 임박·만료 필터 이동이라 대상 식별자가 필요하지 않다. type + id 방식도, 대상별 Nullable FK도 추가하지 않는다. `invalidated_at`도 미채택이며, 알림을 탭한 뒤 목록이 비어 있으면 재고 화면의 빈 상태로 처리한다.
- `title`·`body`는 서버가 발행 시점에 완성해 저장하고 조회 시 재계산하지 않는다. 같은 문구가 웹 푸시 페이로드에도 쓰이기 때문이다.

### 발행 규칙

- 재료 알림은 같은 D-day의 재료를 묶어 한 건으로 표시한다. 임박이 D-3 이내이므로 D-0·D-1·D-2·D-3을 각각 발행하며, 만료를 포함해 하루 최대 5건이다.
- 문구 형식은 `n일 후/오늘 … 만료됩니다` + 실제 유통기한이다.
- 재료 알림 클릭 시 현재 재고의 임박·만료 필터 목록으로 이동한다. 구성원 알림은 이동 없이 읽음만 처리한다.
- `MEMBER_KICKED`는 예외적으로 **퇴출 당사자의 개인 냉장고 ID로 발행한다.** 공유 냉장고 ID로 발행하면 접근이 끊긴 당사자에게 조회되지 않기 때문이다.
- 비활성 개인 냉장고는 알림 생성·푸시를 중단하고, 복귀 시 요약 영역에 만료·임박 개수를 표시한다.
- 수신자 FK만으로 냉장고 접근권한이 증명되지 않으므로 발행·조회 시 별도로 검증한다.

### 활성 냉장고별 노출

- 알림 목록은 사용자의 현재 활성 냉장고 기준으로 조회한다.
- 개인 냉장고에 알림이 쌓인 사용자가 공유 냉장고에 가입하면 개인 알림은 삭제하지 않고 숨긴다.
- 공유 가입 이전의 알림은 소급 지급하지 않으므로 가입 직후 목록은 0개에서 시작한다.
- 공유 냉장고를 탈퇴하면 공유 알림은 숨기고 기존 개인 냉장고 알림을 다시 보여준다.

### 조회·읽음·보관

- 정렬은 `created_at DESC, notification_id DESC`다. 같은 시각의 알림도 안정적인 순서를 갖는다.
- 미로그인 중 발생한 알림도 수신자 행에 안 읽음 상태로 쌓인다.
- **99건은 조회 제한이 아니라 삭제 정책이다.** 사용자·냉장고당 99건을 넘으면 매일 08:00 발행 처리 안에서 삭제한다. 읽은 알림 중 오래된 것부터 지우고, 그래도 초과하면 안 읽은 알림 중 오래된 것부터 지운다. 삭제 단위는 `notification_recipients` 행이고 본문은 수신 행이 하나도 남지 않았을 때만 정리한다. 순서는 `push_notifications` → `notification_recipients` → `notifications`다. 개인 냉장고와 공유 냉장고의 99건은 따로 센다.
- 조회에 `LIMIT 99`를 걸지 않고 페이지당 10건씩 커서 기반으로 반환한다. 커서는 `Base64(created_at|notification_id)`의 불투명 문자열이다.
- 전체 읽음은 현재 사용자·활성 냉장고 범위의 집합 UPDATE로 처리하며 **요청 시작 시각으로 경계를 둔다.** 처리 도중 발행된 알림까지 읽음 처리되어 사용자가 본 적 없는 알림이 사라지는 것을 막기 위함이다. 필터가 걸려 있어도 전체 알림을 대상으로 한다.
- 활성 냉장고 ID는 서버가 인증·권한 확인 후 결정하며 클라이언트 값을 그대로 신뢰하지 않는다.
- 미읽음 수는 앱 전역에서 폴링 하나를 공유해 조회한다.
- 구체적인 인덱스는 테크스펙에서 실제 조회 쿼리와 실행 계획을 확인한 뒤 결정한다.

## 11. PWA 푸시 구독과 발송

**2026-09-07 도입.** 알림함 이벤트와 구독별 전송 작업을 분리한다.

- `user_devices`는 브라우저별 웹 푸시 **구독**이다. `endpoint`(VARCHAR(2048) ASCII, UNIQUE), `p256dh_key`, `auth_secret_encrypted`(BLOB), `encryption_key_version`, `vapid_key_version`, `subscription_version`, `status`(ACTIVE/DISABLED/INVALID).
- 등록은 로그인 사용자 기준으로 처리하며 클라이언트가 보낸 `user_id`를 신뢰하지 않는다. 로그아웃은 해당 브라우저 구독만 DISABLED로 바꾸고 버전을 증가시킨다.
- `push_notifications`는 구독별 **논리 발송 작업**이다. 한 행 = 하나의 논리 이벤트를 하나의 구독 연결 버전에 발송하는 작업이며, 재시도는 같은 행을 사용한다.
- `kind`는 INBOX 또는 RECOMMENDATION이다. **INBOX만 `notification_id`를 연결하고 RECOMMENDATION은 NULL이다.** 이 Nullable FK 하나는 선택 관계이며, 대상 유형마다 FK가 늘어나는 다형 참조와 다르다.
- 상태는 PENDING / PROCESSING / RETRY / ACCEPTED / FAILED / CANCELLED다. `attempt_count`, `next_attempt_at`, `lease_until`, `claim_token`, `expires_at`, `accepted_at`, `last_error_code`를 기록한다.
- UNIQUE(`dispatch_key`, `user_device_id`, `subscription_version`). `dispatch_key`는 INBOX의 알림 ID 또는 추천의 발송일·회원·냉장고를 포함해 결정적으로 생성한다. 재시도마다 새 UUID를 만들지 않는다.
- `payload` JSON에 발송 문구와 내부 이동 경로를 스냅샷으로 저장해, 추천 캐시가 재시작으로 사라져도 재시도할 수 있게 한다.
- DB 원자적 선점으로 작업을 점유하고 `claim_token`이 일치할 때만 결과를 갱신한다. 만료된 임대는 회수한다. 네트워크 발송 중 DB 트랜잭션을 계속 잡아두지 않는다.
- 발송 직전에 구독 상태·소유자·구독 버전·알림 수신 설정·활성 냉장고 접근권한을 재검증한다.
- **`ACCEPTED`는 푸시 서비스의 수락이지 기기 표시·읽음이 아니다.** UNIQUE와 선점은 작업 중복을 줄일 뿐 외부 전송의 exactly-once를 보장하지 않는다.
- `endpoint`도 민감한 구독 정보다. 로그 마스킹·DB 접근 제한, HTTPS 및 지원 푸시 서비스 URL 검증을 적용하고 오류 로그에 원문을 기록하지 않는다.
- 앱 알림함은 `notifications` + `notification_recipients`만 조회한다. `push_notifications`를 합쳐 표시하지 않는다.

## 12. 데이터 저장소 구분

현재 설계: **MySQL 15개 + 인메모리 캐시 1개.**

### MySQL

| 도메인 | 테이블 |
|---|---|
| 회원 | `users`, `social_accounts`, `notification_preferences` |
| 냉장고 | `refrigerators`, `refrigerator_members`, `invite_codes` |
| 재고 | `ingredients` |
| 레시피·조리 | `recipes`, `recipe_ingredients`, `recipe_steps`, `cooking_records` |
| 알림 | `notifications`, `notification_recipients`, `user_devices`, `push_notifications` |

### 애플리케이션 인메모리 캐시 (`in_memory_recommendation_cache`)

- 냉장고별 추천 결과 JSON과 추천 결과 식별자
- 추천 생성 당시 재고 지문과 생성 시각
- 만료 재료 포함·제외 모드
- 다음 추천 푸시 순번
- 날짜별 추천 생성 횟수
- 동일 추천 생성 작업을 공유하기 위한 실행 중 Future

인메모리 캐시는 단일 인스턴스 MVP에는 단순하지만 재시작 시 결과·한도·푸시 순번이 사라지고 여러 서버가 값을 공유할 수 없다. 다중 인스턴스 운영, 재시작 후에도 일일 한도 유지, 서버 간 중복 생성 방지가 필요해지는 시점에 Redis 등 공유 저장소의 원자 증가, TTL, 분산 단일 실행 방식을 검토한다. Redis 전환은 현재 기능이나 ERD의 확정 저장소가 아니다.

### 현행이 아닌 이력 카드

`local_accounts`(users 통합 전 v1 정의)와 `notification_targets`(다형 참조 검토안)는 정의서에 이력으로 남아 있을 뿐 현행 테이블 수에 포함하지 않는다.

## 13. 주요 DB 제약과 애플리케이션 규칙

### 공통 설계 기준

- 내부 PK는 BIGINT 단일 대리키를 사용한다. PK·FK의 타입을 일치시킨다. UUID로 일괄 전환하는 결정은 하지 않았다.
- 모든 BOOLEAN 물리명은 `is_` 접두사를 쓰고 CHECK로 0/1을 제한한다.
- 저장 시각은 UTC, 오전 8시 발송은 Asia/Seoul 기준이다.
- UNIQUE·CHECK·삭제 동작은 문서 설명과 별개로 실제 마이그레이션 DDL로 구현·검증해야 한다.

### DB에서 직접 막는 것

- 닉네임 중복
- v1 로그인 아이디(`users.login_id`) 중복
- `login_id`·`password_hash` 동시 존재 또는 동시 부재
- OAuth 제공자 내부 사용자 식별자 중복, 회원당 같은 OAuth 제공자 중복 연결
- 냉장고별 같은 회원 중복 참여
- 회원당 활성 냉장고 최대 1개(`active_marker`)
- 초대 코드 문자열 중복
- 알림 수신자 `(user_id, notification_id)` 중복
- 조리 기록 멱등키 중복
- 레시피 원천 `(source, source_recipe_id)` 중복
- 레시피 재료 `(recipe_id, ingredient_no)`, 조리 단계 `(recipe_id, step_no)` 중복
- 푸시 구독 `endpoint` 중복, 발송 작업 `(dispatch_key, user_device_id, subscription_version)` 중복
- boolean 계열 값 0 또는 1
- COUNT/WEIGHT 측정값 조합, 레시피 재료의 measure_type별 값·단위 조합
- `kind`와 `notification_id`의 조합(INBOX면 NOT NULL, RECOMMENDATION이면 NULL)

### 애플리케이션 트랜잭션에서 막는 것

- 냉장고 정원 최대 4명
- 냉장고별 재고 행 수가 `capacity`를 넘는 등록
- OWNER만 가능한 초대·추방
- OWNER 탈퇴 시 자동 위임 처리
- 요리 적용 시 여러 재료의 원자적 차감
- 인메모리 기준 냉장고당 일일 추천 생성 10회
- 레시피 부모·재료·단계의 원자적 반영과 역순 버전 차단
- 알림 발행·조회 시 냉장고 접근권한 검증

UNIQUE와 FK를 무조건 생략하는 것이 원칙은 아니다. 현재 한 DB 안의 핵심 정합성 관계에는 적용한다. 서로 다른 서비스·DB, 샤딩된 전역 데이터, 다형 참조, 외부 시스템 ID, 캐시의 논리 참조처럼 물리 제약을 걸 수 없거나 결합 비용이 큰 경우에만 애플리케이션에서 검증한다.

## 15. 구현 전에 남은 확인 사항

### 확정이 필요한 설계

- 버전별 기능 분류에서 `확인 필요`로 남은 항목의 버전 범위
- `refrigerator_type` 도입 여부와 개인·공유 냉장고의 생성·전환 흐름
- 레시피 운영 동기화 계약: 안정 ID, revision 순서, 증분 커서·페이지, 삭제 표시, 단위, 주기·허용 지연·재시도, 커서 저장 위치
- `cooking_records.recipe_id` FK와 `recipe_revision_snapshot` 추가 여부
- ID 없는 생성형 레시피 지원 여부와 추천 캐시 ↔ 레시피 사본 매핑 계약
- 종료한 참여 이력(탈퇴·추방)의 표현 방식
- v1과 v2·v3이 같은 DB를 이어 쓰는지 여부 (OAuth-only 독립 배포라면 로컬 인증 필드 자체가 불필요)

### 운영 정책

- 인메모리 캐시의 TTL·최대 용량·실패 시 카운터 처리와 기준 시간대
- 푸시 발송의 최대 재시도 횟수·backoff·유효 기한·로그 보관 기간·worker 임대 시간
- 새 추천 준비 실패나 한도 도달 시 기존 결과를 발송할지 건너뛸지
- 초대 코드의 유효 시간, 사용 횟수, 재발급 시 이전 코드 처리 정책
- 탈퇴 개인정보와 개인 냉장고 데이터의 실제 보관 기간, 조리 기록·발송 로그의 보관 목적과 기간
- `cooking_count`와 `cooking_records` 성공 건수의 동기화·복구 방식
- `refrigerators.expired_count`의 재시도·재고 삭제·수정 시 중복·누락 방지 구현
- 테크스펙 단계의 쿼리·인덱스·동시성 검증
