## #14 — OCR 인식 상태 4분류

**최종 결론: 미인식 / AI 예상 / 확인 필요 / 확실 네 가지로 나눈다.**

사용자 플로우

1. 사용자가 영수증 사진을 촬영해 제출한다.
   - 영수증 전체를 인식하지 못하면 재고 추가 UI로 이동하지 않고 재촬영 안내 모달을 표시한다.
2. 인식에 성공하면 OCR 분석 결과를 받아 재고 추가 UI로 이동한다.
   - 특정 항목을 인식하지 못한 경우 → **미인식**
   - 정확도가 낮아 사용자 검토가 필요한 경우 → **확인 필요**
   - 높은 정확도로 정상 인식된 경우 → **확실**
   - 유통기한이 없는 상품으로 판단되어 AI가 예상 유통기한을 제공한 경우 → **AI 예상**

핵심은 AI 추정을 **허용할 경우(표기 자체가 없음)와 금지할 경우(표기는 있으나 판독 실패)를 나누는 것**이다. 응답 JSON은 값과 status를 분리해 내려주고, 확인이 필요한 상태는 등록 버튼을 비활성화한다.

> API 반영 상태: `image-analyses` 응답의 `recognitionStatus` / `displayStatus`가 `RECOGNIZED` · `UNRECOGNIZED` · `NEEDS_REVIEW` · `AI_ESTIMATED` 네 값을 사용한다.

## #15 — 냉장고 공유 참여 시 개인 냉장고

**최종 결론: 공유 냉장고에 참여한 동안에는 개인 냉장고 이용이 제한되며, 방장은 다른 공유 냉장고로 이동할 수 없다.**

사용자 플로우

1. 방장이 초대 코드를 생성한다.
2. 다른 회원이 초대 코드로 공유 냉장고에 참여한다.
   - 참여한 시점부터 개인 냉장고를 관리할 수 없다.
3. 방장이 본인의 냉장고를 공유 냉장고로 전환한다.
   - 공유 이후에는 다른 냉장고로 이동할 수 없다.
4. 일반 회원이 공유 냉장고에서 나간다.
   - 공유 냉장고의 재료는 개인 냉장고로 가져갈 수 없다.
   - 공유 참여 이전에 개인 냉장고에 있던 재고는 그대로 유지된다.

검토했지만 채택하지 않은 안: 참여 시 개인 재료를 공유 냉장고로 가져가는 옵션, 누구의 것도 아닌 새 공유 냉장고 생성, 참여 중에도 개인 냉장고를 함께 쓰는 방식.

남은 백엔드 논의 사항
- 공유 참여 중 비활성 상태인 개인 냉장고를 매일 00:00 유통기한 배치 작업에서 제외할지. (공유 종료 후 재계산은 자정 배치로 처리되므로 별도 재계산은 불필요하다는 의견이 있었다.)

## #17 — 매칭되는 레시피가 없을 때의 처리

**결론 정리**

- 부적절한 재료 조합(예: 콜라 닭조림)을 **필터링하지 않는다.** 댓글 참여자 전원이 필터링 불필요 의견이었다.
- 추천은 AI가 재료로 요리를 자유롭게 만들어내는 방식이 아니라 **이미 존재하는 레시피 중 보유 재료로 만들 수 있는 것을 찾아주는 방식**으로 간다.
- 기존의 "재료 3개 이상" 개수 기준은 폐기한다. 리스트 3개가 유통기한만 다른 같은 재료일 수 있어 기준으로 부적절하다. **매칭되는 레시피가 있는지**를 기준으로 삼는다.
- 매칭 실패 시 뭉뚱그린 한 문구가 아니라 **케이스를 나눠 이유를 설명**한다. RECOMMEND-001-2 안내 문구도 이 방향으로 조정한다.

세부 합의
1. 레시피 찾기에서 제외된 재료 표시 → **항상 결과와 함께 표시(a)** + **개수가 많으면 "고기, 양파, 당근 외 1건" 식으로 축약(c)**. 제외 사유는 통일 문구 하나 또는 미표시.
2. 부족 재료가 너무 많은 레시피 → **보유 재료가 레시피의 특정 비중(예: 50%)을 넘지 않으면 표시하지 않거나 AI 응답에서 제외(b)**.

미확정: 매칭 판정 기준(몇 종류 이상 겹쳐야 매칭인지, 매칭률 임계값), 사용할 레시피 DB·API와 매칭 구현 방식.

## #18 — 카테고리 자동 분류 구현 방식

**최종 결론: 방안 3 — 사전 매핑 테이블 + 등록 시점 1회 분류.**

리젝된 안
- **방안 1 매 선택마다 AI 실시간 호출** — 호출 빈도가 사용자 행동에 비례해 늘어 비용·응답 속도 모두 불리.
- **방안 2 자체 분류 모델 학습** — Bechef 사례(FastText, 6,885건 라벨링, 정확도 약 70.5%)를 참고했으나 라벨링·학습·서빙 부담이 현재 팀 규모·일정에 과하다.

채택안 동작
- 자주 쓰이는 재료 500~2,000개를 서비스 오픈 전 AI로 한 번씩 분류해 매핑 테이블을 구축한다(일회성 비용).
- 재료 등록 시점(또는 이름 변경 시)에 테이블을 조회해 `suggested_category`를 저장한다.
- 사용자가 카테고리를 고를 때는 저장된 값과 단순 비교만 하고, 다르면 참고용 헬퍼("달걀은 보통 유제품이에요")만 띄운다. **저장은 막지 않는다.**
- 매핑에 없는 재료는 "기타"로 처리하거나 그 순간만 AI로 보완하고 결과를 테이블에 누적한다.

채택 이유: 런타임 비용이 사실상 없고(재료당 분류 1회), 같은 재료에 항상 같은 결과가 나와 LLM의 비결정성 문제를 피하며, 자체 모델 학습 없이 현재 리소스로 구현 가능하다.

동작 예시: "달걀" 입력 → 테이블 1회 조회 → "유제품" 저장 → 사용자가 "채소" 선택 → 저장값과 다름 → 헬퍼 표시 → "육류" 선택 → 비교만(조회 없음) → "유제품" 선택 → 힌트 없음.

관련 합의(댓글)
- 등록 단계에서도 사용자가 직접 카테고리를 지정할 수 있게 한다.
- OCR·실물 인식 등록일 때만 AI가 자동 분류하고, 결과는 등록 전에 사용자가 확인·수정한다.
- 재고 수정 시에는 AI가 개입하지 않고 사용자가 입력한 이름과 카테고리를 그대로 저장한다(이름을 바꿔도 카테고리를 강제 재분류하지 않는다).
- 레시피는 **재료 이름을 1차 기준**으로 탐색하고, 결과가 부족할 때 카테고리를 보조 기준으로 활용한다.

## #19 — 카테고리 정확도 로직 투자 범위

**최종 결론: 방안 2 — 사용자에게 모든 수정 권한을 일임한다.**

- 카테고리는 주로 필터 목록 표시에 쓰이는 보조 정보라 틀려도 실사용 피해가 작다.
- 정확도 로직(매핑 테이블·분류 등)에 시간을 들이지 않고 구현을 최대한 단순하게 간다. 사용자 입력값을 그대로 저장한다.
- 레시피 매칭은 결국 카테고리가 아니라 재고 이름을 기준으로 이뤄진다고 보았다.
- 추후 정확도를 높일 필요가 생기면 방안 1(경고 알림)을 도입한다.
- 후속: 기능명세서의 요리 추천 페이지에 카테고리 관련 명시가 필요하다.

> **#18과 함께 읽을 것.** #19는 #18에서 파생된 이슈이고 #18보다 나중에 닫혔다. #18은 매핑 테이블 기반 헬퍼(방안 3)를, #19는 매핑 테이블 없이 사용자 전권 위임을 결론으로 두고 있어 두 결론이 겹친다. 실제로 매핑 테이블을 구축할지 확인이 필요하다.

## #31 — 요리 추천·추천 푸시 생성 및 갱신

기본 흐름은 [요리 추천 및 추천 알림 기능 정의서(Notion)](https://app.notion.com/p/3cf836d5c371800aa7d9de33ac9c8420)를 따르고, 아래는 댓글에서 확정·변경한 최종 사항이다.

### 1. 추천 생성 시점

재고 등록·수정·수량 변경·요리 적용·삭제 시점에는 AI를 바로 호출하지 않는다. 사용자가 홈 또는 추천 페이지에 진입했을 때 현재 재고 상태와 캐싱된 추천 생성 당시 재고 상태를 비교한다.

- 일치하면 기존 추천을 그대로 사용한다.
- 일치하지 않으면 최신 재고 기준으로 AI를 한 번 호출한다.
- 생성하는 동안에는 기존 추천 목록을 보여준다.
- 새 추천이 준비된 뒤 화면이 다시 갱신되면 최신 추천을 보여준다.
- 기존 추천도 없으면 준비 중 화면을 표시한다.

유통기한을 여러 번 수정해도 수정 횟수만큼 호출되지 않고 최종 재고 기준으로 한 번만 호출하므로, **별도의 5~10분 배치 주기는 두지 않는다.**

### 2. 요리 적용 후 목록 유지

적용 시 사용 재료를 한 번만 차감하고 AI를 새로 호출하지 않는다. 뒤로 가기로 돌아오면 프론트가 보관한 기존 목록을 그대로 보여주고, 홈·추천 페이지에 새로 진입했을 때 갱신 여부를 판단한다.

### 3. AI와 서버의 역할

- AI: 추천 요리, 요리별 필요 재료, 재료별 필요 수량·무게를 생성한다.
- 서버: 필요량과 보유량을 비교해 `미보유` / `부족` / `적합`을 계산한다.
- 추천 목록에서는 상태만 표시하고, 정확한 개수·g·ml는 요리 상세에서 보여준다.
- 소금·물처럼 재고 수량으로 비교하기 어려운 재료는 상세에 포함하되 `미보유`가 아니라 **`별도 준비 재료`**로 표시한다.

### 4. 추천 생성 한도 안내

하루 10회 한도는 유지하되, 사용자가 버튼으로 직접 소모하는 구조가 아니므로 `오늘 새 추천 N회 남음`을 상시 표시하지 않는다. 대신 홈·추천 화면에서 다음을 안내한다.

- 재고가 변경된 경우에만 새 추천이 자동 생성된다는 점
- 기존 추천 재조회·정렬 변경은 횟수에 포함되지 않는다는 점
- 하루 한도에 도달하면 기존 추천이 표시된다는 점
- 새 추천은 다음 날 다시 생성할 수 있다는 점

구체적인 안내 방식은 `?` 버튼 + 팝업 등을 후보로 두고 화면 설계에서 결정한다.

### 5. 수동 추천 버튼

한 번의 AI 호출로 여러 요리를 추천하므로 `새로운 요리 또 추천받기` 버튼은 **추가하지 않는다.**

### 6. 추천 푸시

- 추천할 요리가 있으면 요리명을 포함해 전송한다. 예: "오늘은 두부김치 어때요?"
- 추천할 요리가 없으면 재료 등록을 유도하는 문구를 쓴다. 예: "냉장고에 재료를 넣어주세요"
- 푸시를 누르면 특정 요리 상세가 아니라 **추천 페이지**로 이동한다. 확인 사이 재고가 바뀌었다면 푸시에서 안내한 과거 요리를 유지하지 않고 현재 재고 기준 추천을 제공한다.
- 추천 푸시는 서비스 내부 알림 목록에 저장하지 않는다.
- 추천은 푸시 5분 전인 07:55부터 확인·생성한다. 테스트에서 실제 AI 응답 시간을 측정해 필요하면 시작 시각을 조정한다. 08:00까지 준비되지 않은 경우의 예외 처리는 구현 단계에서 결정한다.

### 7. 푸시 추천 순서

추천 요리를 순환(로테이션)하는 방식은 **적용하지 않는다.** 재고가 변경되지 않았다면 매일 현재 추천 목록의 1순위 요리를 푸시한다. 다양한 요리를 번갈아 소개하는 것보다 만료·임박 재료를 빠르게 소진할 우선순위 높은 요리를 안내하는 것이 서비스 목적이기 때문이다. 재고가 바뀌면 최신 재고 기준으로 목록과 우선순위를 다시 판단한다.

## #33 — 알림 기능 정책

본문의 초기안 중 일부는 댓글 논의로 뒤집혔다. **아래 최종 논의 결과가 기준이다.**

### 1. 내부 알림과 휴대전화 푸시 분리

사용자의 알림 설정은 **휴대전화 푸시 수신 여부에만** 적용한다. 푸시를 해제해도 서비스 내부 알림은 생성되어 목록에 표시된다.

```text
푸시 해제 사용자 → 푸시 전송 안 함 → 내부 알림은 표시
푸시 허용 사용자 → 푸시 전송      → 내부 알림도 표시
```

추천 요리 알림은 휴대전화 푸시로만 제공하고 내부 알림 목록에는 저장하지 않는다.

### 2. 알림 문구

상태별 문구와 실제 유통기한을 함께 표시한다.

| 상태 | 문구 | 함께 표시 |
|---|---|---|
| 오늘 제외 임박 | `2일 후 우유가 만료됩니다.` | `2026년 9월 4일` |
| 오늘 만료 | `오늘 우유가 만료됩니다.` | `2026년 9월 2일` |
| 이미 만료 | `우유가 만료되었습니다.` | `2026년 9월 2일` |

`오늘`·`2일 후`로 남은 기간을 이해하게 하고, 실제 유통기한을 함께 적어 나중에 확인해도 정확한 날짜를 알 수 있게 한다.

### 3. 비활성화된 개인 냉장고의 알림

개인 냉장고를 쓰지 않는 동안에는 **새 만료·임박 내부 알림을 생성하지 않고 푸시도 전송하지 않는다.** 비활성화 전에 생성된 기존 알림 목록은 유지한다.

복귀 시 비활성 기간의 알림을 날짜별로 뒤늦게 생성하지 않고, 현재 재고 상태를 확인해 알림 페이지 최상단 요약 영역에 **만료 재고·임박 재고 개수**를 보여준다. 복귀 이후 발생하는 알림부터 다시 목록에 추가한다.

이유
- 냉장고당 재고가 최대 100개라 복귀 시 현재 상태 확인 부담이 크지 않다.
- 확인할 수 없는 냉장고의 알림이 쌓이면 오래된 알림이 99개 한도를 차지한다.
- 만료·임박 알림은 장기 기록보다 현재 상태 안내 성격이 강하다.
- 복귀 시 중요한 정보는 비활성 기간의 날짜별 알림이 아니라 현재 만료·임박 재고다.

**적용하지 않기로 한 초기안:** 선택하지 않은 냉장고도 알림을 계속 생성 / 비활성 기간 알림을 DB에 누적 / 복귀 시 누적 알림을 한꺼번에 표시.

### 4. 알림 관리 기준

알림은 냉장고에서 발생하지만 푸시 설정·읽음 상태는 사용자마다 다르므로 **냉장고와 사용자를 함께 기준**으로 관리한다. 공유 냉장고에서 같은 상황이 발생해도 구성원별로 알림을 제공해 읽음 상태를 독립적으로 관리한다. 목록에는 현재 사용 중인 냉장고에서 발생한 알림만 최신순으로 보여준다.

ERD 반영 예정 사항(댓글)
- `notifications`에 `refrigerator_id` 컬럼 추가 — 냉장고별 알림 필터링용
- `(user_id, refrigerator_id, created_at)` 인덱스 추가
- `created_at` 노트를 '발송 시각' → '발생 시각'으로 정정 (푸시 없이 DB에만 저장하는 알림이 있으므로)

### 5. 알림 목록 UI

최상단 요약 영역에 현재 냉장고의 **만료된 재료 개수**와 **임박한 재료 개수**를 함께 표시한다. 이 영역은 과거 알림 요약이 아니라 현재 재고 상태 기준이다.

각 알림에 표시할 정보: 읽지 않은 알림 표시, 만료/임박 유형, 알림 제목, 대상 재료와 개수 요약, 실제 유통기한, 알림 발생 날짜와 시간, `더보기`.

### 6. 알림 선택 후 이동

`더보기`는 개별 재고 상세가 아니라 해당 냉장고의 필터가 적용된 재고 목록으로 이동한다.

- 임박 알림 → 냉장고 관리 페이지의 임박 필터 목록
- 만료 알림 → 냉장고 관리 페이지의 만료 필터 목록

만료 재고 목록에는 재고를 정리할 수 있는 버튼을 추가한다. 이에 따라 **`MY-004 만료 재고 목록 정리` 화면은 삭제하고 냉장고 관리 페이지의 만료 필터 화면으로 통합한다.**

안내했던 재료가 이미 수정·삭제됐다면 이동 시점의 현재 재고 기준 목록을 보여주고, 해당 재료가 없으면 필터가 적용된 빈 목록을 표시한다.

### 7. 알림 보관 정책

사용자별 **최대 99개**만 보관한다. 한 달 같은 별도 보관 기간을 두고 일괄 삭제하는 방식은 쓰지 않는다.

100번째 알림이 생성되면 다음 우선순위로 기존 알림 하나를 **즉시 삭제**한다.

1. 읽은 알림 중 가장 오래된 알림
2. 읽은 알림이 없다면 읽지 않은 알림 중 가장 오래된 알림

읽지 않은 알림은 최대한 보존하지만, 읽지 않은 알림만으로 99개를 초과하면 가장 오래된 것을 삭제한다.

화면의 미확인 알림 개수는 99개 이상이면 `99+`로 표시한다.

### 8. 유사 서비스 사례 적용 여부

Google Home·Ring 사례를 검토했지만, 우리 개인 냉장고는 단순히 선택되지 않은 상태가 아니라 **비활성화되는 구조**라는 차이가 있다. 따라서 다른 공간의 알림을 계속 생성하거나 푸시만 중단하고 기록을 유지하는 방식을 그대로 적용하지 않고, 선택 상태·내부 기록·푸시를 분리할 수 있다는 참고 사례로만 활용한다.
